# TerraLab AI Phase 1: research and architecture

Verified 21 October 2026 against the repository and official sources below. This is the AI initiative's Phase 1, separate from earlier scientific-platform phases with similar names.

## Decision

Use a TerraLab-native, read-only text runtime in Next.js Node route handlers. Add no agent framework or database migration. Call DeepSeek's official API directly through a typed provider interface, with optional local Ollama. Do not embed or launch DeepSeek Harness in the application. Calling a DeepSeek model does **not** mean running Harness or obtaining free inference.

A model provider performs inference. A harness manages an agent loop, tools, permissions and sessions. A tool backend implements operations and enforces authorization independently of the model. Phase 1 has a deterministic context reader and a single text-generation request, with no model-dispatched tools. A future agent can reuse the context and provider interfaces while adding narrowly validated tools separately.

## Repository baseline and preserved boundaries

Source inspection covered the repository tree, package and deployment configuration, routes, shared schemas, auth/persistence, editor state, laboratory and solver entry points, queue/worker, collaboration and SQL policies. Relevant sources:

- Next.js 16.4.2 App Router, React 19.3.1, TypeScript, Tailwind 4, Radix UI, Lucide, Zustand and TanStack Query. `apps/web/components/studio.tsx` owns the existing editor; `research-dashboard*.tsx` owns the library. Existing routes are `/`, `/studio`, `/projects`, `/collaboration`, and the four scientific API proxies. There was no existing AI runtime or credential store.
- `packages/shared/src/model.ts` validates project schemas 1/2 and anchor, receiver, obstacle and trajectory entities. Obstacles can have schema-2 physical heights; receivers have stationary, velocity, linear, circular, random and waypoint mobility. `geometry.ts`, `mobility.ts` and `solver.ts` implement browser geometry, motion and calibrated-range solving.
- `packages/shared/src/laboratory.ts` supplies measurement/estimator schemas; `services/api/terralab/{main,engine,estimators,physics,experiments}.py` implement FastAPI, scientific solving and reproducible experiments. Supported laboratory observations include TOA, pseudorange, TDOA, RTT, AOA, RSS and hybrid configurations; estimators include LS, WLS, robust NLS, RANSAC, MLE, EKF and UKF.
- `apps/web/lib/laboratory.ts` validates results with requests, records, frames and summaries; local history uses IndexedDB. `research.ts` retrieves immutable cloud artifacts with manifest/hash checks. Production uses Supabase jobs, leased Python workers and private result chunks. `worker.py`, `cloud.py`, `worker_wake.py` and `runtime.py` separate user-token API access from worker service credentials.
- `persistence.ts` uses Supabase Auth and JWT-scoped reads, checked save RPCs, versions and local recovery. SQL policies use `private.project_role` for owners/editors/viewers and inherited team access. Collaboration adds invitations, access requests, notifications and explicit grant management. AI uses project SELECT RLS and never reads these private collaboration tables.
- Vercel hosts Next.js; Render hosts FastAPI/worker. Existing Vercel API duration is 60 seconds. Solver code, queue behavior, schemas, migrations and existing workflows are preserved. The only hosting-config addition disables Vercel auto-deploys for `codex/ai-studio-phase-1` so the authorized push does not publish a preview; other branches retain their existing behavior. See [Vercel branch deployment controls](https://vercel.com/docs/project-configuration/git-configuration#git.deploymentenabled).

## DeepSeek Harness findings

The official [project README](https://github.com/deepseek-ai/deepseek-harness) describes a Cordis plugin architecture and explicitly warns that its developer preview will introduce breaking changes. CLI launch is `npx @deepseek-ai/dsh web`; source builds use pnpm. Registry metadata on the verification date reported `@deepseek-ai/dsh` **0.2.1-rc.2**. Source `package.json` declares Node `^22.19.0 || >=24.0.0` and `pnpm@11.28.5`, beyond TerraLab's current declared Node floor of 20.9. The published top-level package did not declare `engines`; that is not proof of older-Node compatibility. [Package metadata](https://registry.npmjs.org/@deepseek-ai/dsh/latest), [source package](https://github.com/deepseek-ai/deepseek-harness/blob/master/package.json).

Harness is [MIT licensed](https://github.com/deepseek-ai/deepseek-harness/blob/master/LICENSE); reused substantial code would require retaining its notice and reviewing third-party notices. No Harness code is copied here.

The [quickstart](https://deepseek-harness.github.io/deepseek-harness/en/guide/quickstart) requires selecting a filesystem workspace and exposes coding operations. The [provider guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/providers.md) supports built-in providers such as DeepSeek, OpenAI, Anthropic, Moonshot and ZAI plus custom Chat Completions, Responses and Anthropic Messages endpoints. Credentials are write-only through its UI but stored in `$DSH_HOME/.credentials.yaml`; configuration references that file. Environment detection is not a live credential check. TerraLab must not reuse that host-wide credential mechanism as a multiuser store.

The [architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md) allows tool-registry plugins and customized profile trees. A purpose-built composition could theoretically register only simulator tools. That would require auditing every mounted plugin and preventing filesystem, shell, database and inherited capabilities from entering the tree. The stock Web or SDK profile is not such an allowlist, and its host-session authentication does not implement TerraLab project authorization.

The current [Python SDK guide](https://deepseek-harness.github.io/deepseek-harness/en/guide/python-sdk) replaces guessed SDK paths: Python >=3.10, supported platform wheels, explicit workspace and Harness home, and a matching bundled CLI runtime. PyPI reported `deepseek-harness-sdk` **0.2.1rc2**, MIT. The minimal SDK profile still exposes a persistent shell, image reading and working-directory operations, defaults to broad host access, persists logs, and describes default session-log uploads. These assumptions are unsuitable for TerraLab user requests. [Python package metadata](https://pypi.org/pypi/deepseek-harness-sdk/json).

The official [safety notice](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md) says the preview has not undergone a security audit, can access host resources, and cannot rely on sandbox/approval controls as its only isolation. The [public-deployment guide](https://deepseek-harness.github.io/deepseek-harness/en/guide/public-deployments) adds trusted hosts, launch-token/session-cookie authentication, TLS, proxy upgrades, cookie rewriting and listener restrictions. A public URL alone is insufficient. These are additional runtime operations, not a drop-in Next.js component.

**Fit:** useful reference architecture and optional developer-operated tool in a disposable workspace. A separately isolated server runtime is conceivable after further auditing, but is rejected for Phase 1. Neither the JS/TS process runtime, Python SDK subprocess, nor plugin system provides a sufficiently small, established deployment boundary for this application's current needs.

## Provider protocols and verified behavior

**DeepSeek:** bearer user API key, fixed `https://api.deepseek.com` destination, `GET /models`, `POST /chat/completions`, JSON messages and SSE when `stream: true`. The current docs list `deepseek-flash` and `deepseek-v4-pro`; names are documentation examples only. The UI discovers models at runtime and the server checks membership on every turn. Thinking is explicitly disabled in this text-only foundation. Tool calls are supported upstream, but none are advertised or executed here. [First call](https://api-docs.deepseek.com/), [models API](https://api-docs.deepseek.com/api/list-models/), [tool behavior](https://api-docs.deepseek.com/guides/tool_calls/).

**User-supplied hosted provider:** DeepSeek BYOK is the supported hosted route in this phase; each signed-in user's cookie is decrypted only for that user. The provider interface is extensible, but arbitrary endpoints are deliberately excluded. This avoids treating all compatible-looking services as equivalent.

**OpenCode Console:** evaluated, not implemented. Its [official catalogue](https://opencode.ai/v2/docs/console/models) now distinguishes per-model Responses, Messages and Chat Completions endpoints. API keys, credits and billing belong to the user; model availability/pricing may change. Adding it safely requires provider-specific protocol discovery and tests rather than applying one generic URL to every listed model. No promise of permanent free inference is made.

**Ollama:** optional loopback-only local-development adapter. `GET /api/tags` lists installed models, `POST /api/show` verifies `completion` capability, and `POST /api/chat` streams NDJSON. The selected model must be manually installed and chosen; no pull endpoint is called. A remote deployment cannot address the user's machine through its own localhost. [List API](https://docs.ollama.com/api/tags), [show API](https://docs.ollama.com/api-reference/show-model-details), [chat API](https://docs.ollama.com/api/chat). Upstream [tool calling](https://docs.ollama.com/capabilities/tool-calling) and schema-constrained [structured outputs](https://docs.ollama.com/capabilities/structured-outputs) are model/runtime dependent; Ollama Cloud currently excludes structured outputs. Neither feature is assumed or used by Phase 1.

## Limits and deployment assumptions

DeepSeek distinguishes invalid credentials (401), insufficient balance (402), rate limits (429), and server failures (500/503). Quotas are account/model dependent and may change. Listing models verifies connectivity/authentication, not sufficient funds or successful generation. SSE keep-alives are ignored by the parser. No automatic paid-provider switching or retry loop occurs. [Errors](https://api-docs.deepseek.com/quick_start/error_codes/), [rate limits](https://api-docs.deepseek.com/quick_start/rate_limit/).

The boundary is browser → same-origin Next route → verified Supabase user → existing RLS project read → minimized summary → selected fixed provider → redacted text stream. Encryption and provider secrets stay in server modules. The current Supabase `getUser(jwt)` [documentation](https://supabase.com/docs/reference/javascript/auth-getuser) confirms server verification, unlike trusting a browser session object. The changelog was reviewed; the upcoming [TLS cipher removal](https://supabase.com/changelog/cbc-tls-ciphers-deprecated) does not change this API surface or require a schema change.

The implementation is tested with mocks and a local protocol fixture. No user AI key or running Ollama instance was supplied, so live inference is **not validated**. See the setup, security and Phase 1 report for exact checks and remaining work.

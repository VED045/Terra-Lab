## Architecture and security decisions

- Research rejects embedding/launching DeepSeek Harness's coding-agent UI/runtime. Its preview status, broad workspace/shell defaults, host credentials and process/session assumptions do not match TerraLab's authorization/deployment boundaries.
- Reuse fetch, Zod, React, existing Supabase Auth/RLS and design tokens. No AI SDK, Harness or other package is added, and no lockfile, domain schema, solver or migration changes are needed.
- Server-verified user identity selects the encrypted credential; project membership never grants access to a colleague's key. Production has no shared environment-key fallback. A missing encryption key makes browser saving unavailable with an explicit message.
- Context omits project prose, identities, coordinates, raw measurements/results and collaboration records. Cloud access is rechecked each turn through existing project RLS; browser snapshots cannot override it.
- No executable model tools exist. Suggestions are text. Verified activity is generated by application code, with no claim to have executed edits or experiments.
- `apps/web/vercel.json` disables automatic Vercel deployment only for this delivery branch, following the [official branch rule](https://vercel.com/docs/project-configuration/git-configuration#git.deploymentenabled). This supports pushing without publishing a preview. Existing Render auto-deploy is already off. No hosting API mutation or deploy command is performed.

## Operational assumptions and remaining work

See `PROVIDER_SETUP.md` for the exact setup and smoke-test commands and `SECURITY_AND_LIMITS.md` for resource limits and threats. Production requires HTTPS, existing Supabase policies, outbound provider access and server-only encryption configuration. The cookie is browser-local encrypted persistence with seven-day expiry, not a synchronized secret vault or server-revocable credential database. Provider retention, cost and quota depend on the user's account. Stop cannot reverse work or charges already incurred.

AI Studio reads saved configurations, not unsaved editor drafts or measured result artifacts. Optional selected cloud run configuration is supported through `?project=<uuid>&experiment=<uuid>` and project-scoped authorization. There is no persistent chat history, cost meter, arbitrary provider URL, automatic fallback, distributed AI rate limiter, remote Ollama bridge or claim of scientific correctness for generated prose.

Before declaring live inference validated, a user must configure their own provider and run the opt-in smoke test or send a successful response through AI Studio. Hosted Supabase and production/browser integration acceptance must be performed separately in an authorized staging environment.

Phase 2 remains the design and implementation of narrow, typed simulator tools with fresh authorization, validation, explicit action approval and auditable outcomes. Phase 3 remains an isolated test-running agent with bounded execution and provenance. Neither is started here. Rollback is reverting this additive application commit; no stored research data or database schema requires rollback.

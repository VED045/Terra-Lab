# TerraLab Phase 4A security review

20 October 2026. Baseline `e2e84ba`; changes remain local and uncommitted. **Production acceptance is blocked pending real hosted verification.** No claim of a complete penetration test, independent cryptographic attestation, or real-time collaboration is made.

## Trust boundaries inspected

Browser public Supabase key + user JWT → checked PostgREST RPC/RLS and private Storage; browser → Next proxies → FastAPI forwarding the same caller token; separate worker → service credential → leased DB queue and raw artifacts. Local filesystem jobs are development-only. The frontend does not receive the worker credential.

Public keys do not authorize bypassing RLS; service credentials do bypass it. This matches the reviewed [Supabase Storage access-control contract](https://supabase.com/docs/guides/storage/security/access-control) and [database RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security). Server-side checks and SQL grants/RLS are exercised independently of hidden buttons.

## Validation and secret handling

All automated SQL identities are fake UUIDs in a fresh in-memory database. HTTP worker fixture keys are obviously fake. Browser tests explicitly blank Supabase public config and start owned loopback processes with separate data. Secret values were not printed or committed. The hosted read-only probe fetched public Auth settings and HEAD table probes with `limit=0`; it retrieved no project rows or Storage contents.

The staging mutation harness is supplied for review and was **syntax checked only**. Automatic approval review rejected its attempted execution because an exact external staging destination and create/delete scope were not explicitly approved. The rejected action was not executed or retried indirectly. Saving the source and `node --check` were the safe alternative. No hosted-test pass is recorded.
